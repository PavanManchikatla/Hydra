## ⚑⚑ READ THIS BEFORE THE NUMBERS: 0.250 OF THIS LEG'S 2.000 CPU-HOURS BOUGHT NOTHING

This is the **first leg to include the `vendored-gguf` target**, and in CI that target is
**structurally incapable of doing its job**. It exists to drive `gguf_init_from_file` inside
`llama.cpp`; audit **L1** means CI never builds the real engine, so `hydra_engine_sys::gguf_probe`
is never called. What the target actually did was re-run the **hardened Rust** parser — which the
`gguf` target already covers — and then nothing.

**It nevertheless printed `verdict=GREEN`**, because the driver computed the verdict as
"no crashes", and a no-op never crashes:

```
target=vendored-gguf seed=1000003 iterations=127886336 cpu_seconds=112.5 crashes=0 verdict=GREEN
```

**868 410 368 iterations and 900.0 CPU-seconds of a parser that was never invoked.** PROJECT_STATE
§0(b) correctly said this target's CI status is *"unavailable, never green"* — but **the log said
GREEN**, and rule 16 makes the log the thing a receipt quotes. The record's intent was right; the
code did not implement it. That gap is §7.62, found while writing this receipt.

**Fixed after this run** (so this receipt documents the leg *as it ran*): the target now reports
`verdict=UNAVAILABLE` with its reason, consumes **zero** budget, and the runnable targets split the
whole allocation. The classify step additionally **fails** if a required target reports UNAVAILABLE,
or if `vendored-gguf` reports GREEN in CI — because that would mean either L1 is fixed (promote it
to required) or the target is again claiming a green it did not earn.

**Accordingly this receipt counts 1.750 CPU-hours, not 2.000.**

## What this receipt does and does not establish

**Does:** seven parsers survived **11.3 billion** structure-aware hostile inputs without a panic,
abort, or unproven slice, at the caps and generators described in `crates/hydra-fuzz`.

**Does not:**

* **It is not 24 CPU-hours.** It is 4.150 cumulative, and the DoD stays open.
* **It says nothing about the engine's own GGUF path.** That is precisely what `vendored-gguf`
  exists for and precisely what CI cannot run (L1). Its status here is **UNAVAILABLE, not green** —
  and as of §7.62 the log finally says so in those words.
* **It is not coverage-guided.** `hydra-fuzz` is deterministic and structure-aware, with no feedback
  loop; the trade is `(seed, iteration)` reproduction and a stable-Rust CI arm. `cargo-fuzz` over the
  same entry points remains an owed additive upgrade (§8).
* **It cannot see a hang or a large-but-legal allocation** — no timeout oracle, no allocation
  ceiling. Both are named §8 rule-19 gaps, not implied coverage.
* **It does not reach `Worker::on_frame`** — it stops at `wire::decode`, so the role gate, the C4
  fence, M9 sequencing and every SM transition are unfuzzed (§8).
* **Absence of a crash is not absence of a bug.** It is absence of *this* class under *these*
  generators.

## Reproducing any case

Every case is a pure function of `(target, seed, iteration)`:

```
cargo run --release -p hydra-fuzz --bin hydra-fuzz -- --target wal-record --seed 1000003 --replay 412345
```

`--replay` restores the default panic hook, so the operator gets the backtrace the campaign
deliberately suppresses.
